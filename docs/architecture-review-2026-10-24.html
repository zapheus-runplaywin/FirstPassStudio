FirstPass Studio · architecture, design and UX review · 24 October 2026

Studio is in good shape. Fourteen decisions would make it simpler and harder to break.

The whole repository was read for this review: the local helper (server.js and its twelve modules), the 42 graphics and Studio pages, the Mac app, the Stream Deck plugin, the tests and the workflows. Nothing here is a bug report from a stream night. These are places where the design has grown past the shape it started with, and where one choice now saves many small fixes later.

Each finding ends in a decision for Matt. Nothing changes until a decision is made, and every change goes through its own pull request.

What to keep

These are deliberate choices that are working, and the review found no reason to revisit them.

No framework, no build stepPlain Node, plain HTML. Two runtime dependencies. The helper starts without npm install and a page is one file you can open and read.
One data folder, versionedEverything saved lives outside the app, with numbered migrations and a backup before each one. iCloud placement is handled carefully (size checks, refusal to start empty).
Real tests in a real browser273 tests, every page opened in Chromium against a stand-in PlayHQ, Stream Deck links read from the OpenAPI file so docs and code can't drift.
Graphics fail quietlyA page shows an error only before its first load; after that a hiccup goes to the log, never to the stream. The 15 MB capped log with page errors forwarded is exactly right for stream night.
WebSocket for scene updatesSwitching from server-sent events after the six-connection stall was the correct diagnosis and fix, and the hand-rolled WebSocket is small and readable.
Settings belong to the competitionThe rule that anything competition-specific lives in the setup and config.json keeps only machine settings has been held to. It should stay a hard rule.
Comments explain whyEvery module opens with a paragraph on what it is for and what it deliberately doesn't do. That is rarer than it should be and worth protecting.
Manual overrides everywhereAutomatic game selection, the PlayHQ clock and sequences all yield to a press. That rule is visible in the code and should stay.

Reliability

D1

Read PlayHQ on a timer in the helper, not when a page happens to ask

High

Finding. The helper reads the live score only inside four HTTP requests: when a page fetches the scoreboard, the goals, the stats or the worm. There is no timer of its own. Everything else that reacts to the game reads the board the pages last refreshed: the game triggers that start sequences ("It's full time", quarter breaks), the super shot song, the streak and moment animations, and the goal order.

So the live state of the game depends on which windows are open. With the default reload on show, a hidden scoreboard source is unloaded to a blank page and stops polling. If the control page is also closed and the Output page is the only thing open, PlayHQ is not read at all, the board freezes at its last score, and a sequence waiting for full time never starts. That is an invisible dependency, and it will fail on a night when the scoreboard is off screen for a sponsor break.

The bandwidth rule ("pages only talk to the helper, the helper alone calls PlayHQ") also becomes exact: one reading every playhqRefreshSec whatever is open, instead of one per polling page coalesced by the cache.

Recommend
One timer in the helper that runs the existing refresh every playhqRefreshSec while a game is being followed and scoring has opened. Pages keep polling or move to D11, but they only read. Game triggers then work with any windows open.
Alternative
Leave it pull-driven and document that the control page must stay open for triggers. Cheaper, but it moves the rule into people's heads.
Risk
Low. The refresh already tolerates being called often; the stand-in PlayHQ tests cover following a game.
Evidence: refreshFromPlayhq is called from exactly four routes in server.js (scoreboard, goals, stats, worm) and nowhere else. scene.game(gameSnapshot()) runs every second but only reads the board. scene.html sets a hidden source's iframe to about:blank when reloadOnShow is on.
D2

Write every settings file atomically

High

Finding. Every JSON file Studio saves is written in place with a plain write: the scene, sequences, music, outputs, sponsors, the control file, competition settings, the athlete register and the data version. A crash, a kill from the app's restart loop, or a power cut in the middle of a write leaves a half-written file. On the next start that is a JSON parse error, which most modules catch by falling back to empty, so the symptom would be "my scene is gone" rather than an error message. The migration backups protect against a bad upgrade, not against this.

Recommend
One shared writeJson in datadir.js that writes to a temporary file beside the target and renames it over the top, and every module uses it. Fifteen call sites, no behaviour change. Add a one-line "could not read, kept the last good copy" log when a file fails to parse.
Alternative
Only do it for the files that are hard to rebuild (scene, sequences, sponsors, competitions) and leave the state files.
Risk
None of note. Rename is atomic on APFS and on iCloud Drive's local folder.
Evidence: 17 fs.writeFileSync sites across competitions.js, datalocation.js, migrations.js, music.js, outputs.js, scene.js, sequences.js, server.js, sponsors.js, viewers.js, desktop/main.js; two local writeJson helpers already exist with the same body.
D3

Decide who on the network may drive Studio

High

Finding. The helper listens on every network interface, answers every request with access-control-allow-origin: *, and has no authentication. That is by design: the links use the Mac's .local name so a phone can open the control page, and the Stream Deck plugin talks to it directly. But the same openness covers the endpoints that switch scenes, start sequences, change scores, upload and delete media, save competition settings and delete a competition. Anyone on the venue Wi-Fi with the Mac's name can do all of that, and the wildcard CORS header means any web page open in any browser on that network can too, without the person noticing.

For a one-person setup at a netball centre the practical risk is a mis-tap, not an attacker. But it is a decision that should be made on purpose, and it gets harder to change once more devices depend on the links.

Recommend
Keep listening on all interfaces (the phone links matter) but drop the wildcard CORS header, so only pages served by Studio itself and non-browser clients like the Stream Deck plugin can call the API. Then add one setup toggle, default on: "Let other devices on this network change things". Off, writes from other addresses get a plain 403 and the reason. Reads stay open.
Alternative
Leave it as it is and accept that the venue network is trusted. Write that down in the README so it is a choice, not an accident.
Risk
Low. Any page that calls the API from another origin (there shouldn't be one) would show up in the page test.
Evidence: send() in server.js sets the wildcard header on every response; .listen(PORT) has no host; no route checks the caller.
D4

Say plainly when the port is taken

Medium

Finding. The HTTP server has no error handler. If port 8080 is already in use (a stray npm start, a second copy of the app, another tool), Node throws, the helper exits, the Mac app restarts it up to five times a minute and then shows "off air". Nothing tells you why.

Recommend
Catch the listen error, log "Port 8080 is already in use" and exit with a distinct code the app recognises and shows in the menu and the off-air page, with the fix (quit the other Studio, or change the port in config.json).
Risk
None.
D13

Pin and bump dependencies

Low

Finding. The app pins exact versions, which is the right rule. Electron is on 44.8.0 with 45.0.0 out. The Stream Deck plugin uses a caret range (^3.0.2) for its one dependency, unlike everything else in the repository.

Recommend
Bump Electron to 45 and pin the plugin's dependency exactly, in the next housekeeping PR. Consider letting Dependabot or Renovate open these so the versions rule needs no one to remember it.

Architecture

D6

Split server.js into the modules it already contains

Medium

Finding. server.js is 3,100 lines. It is well commented and already divided by rulers, but it holds seven separate things: the PlayHQ client (sessions, GraphQL, caches), the round and fixture logic, the scoreboard engine (board, actions, clock, super shots), goal order with streaks and moments, athletes and photos, finals and team sheets, and the HTTP router. Everything else in the repository is a module of 200 to 1,000 lines with one job, so this file is the exception, and the one most PRs touch.

Size alone is not a problem. The cost is in review and in risk: a change to the goal order is in the same file as the router, shared module-level state (CONFIG, boards, caches) is reachable from everywhere, and new routes keep being added to a 150-line if chain.

Recommend
Move code without changing it, one module per PR so each stays reviewable: playhq.js (session, gql, structure, ladders, rounds, live feed), board.js (scoreboard engine and goal tracking), athletes.js, games.js (round choice, fixtures, up next, auto select). server.js keeps the router and the glue. The tests already exercise all of it through HTTP, so a pure move is safe.
Alternative
Leave it. It works, and the comments make it navigable. Choose this if the pace of new features is about to slow.
Risk
Low per PR, but it takes a few. Module-level state has to be passed in deliberately, which will expose a couple of hidden couplings. That is also the benefit.
D7

One list of pages instead of three

Medium

Finding. Which graphics exist, what options they take and what to call them is written in three places by hand: the Docs page (43 page links), the Output page's "Add a page" options in pageoptions.js (30 pages), and the example-graphics script (32 pages). There are 42 pages in public/. The three lists already disagree, so a new graphic needs three edits and a new option needs two, and the rule "add it to pageoptions as well as the home page" has to be remembered.

Recommend
One pages.json (name, file, group, options with their quick picks, whether it animates away, whether it appears in examples) served at /api/pages. The Docs page, the Add a page dialog, the examples script and the page test all read it. The page test then fails when a page is missing from the list.
Risk
Low. The Docs page's prose about each page stays as it is; only the registry moves.
D9

Break the Output page's script into one file per section

Medium

Finding. output.html is 2,230 lines, 1,685 of them one inline script covering six features: video output, music, sequences, scenes, sources and the media folder. It is the page you will keep changing most, and every change to any section is a diff in one file. A long inline script also can't be unit tested on its own; today it is covered only by opening the page.

Recommend
Move each section's script into public/output/<section>.js, loaded in order by the page, with the HTML unchanged. Pure move, same globals. Then the sequence editor or the music player can get a test of its own later.
Alternative
Leave it as one file, since the page itself was recently reorganised and works.
Risk
Low. The page test and the pop-out, sequence and music tests cover the behaviour.
D11

Push the scoreboard over the socket the pages already hold

Low

Finding. Studio pages follow the scene over one WebSocket, but the game still arrives by polling: the scoreboard every second, the control page every two seconds plus teams every ten, goals every two, the countdown every five, and three pages ask for the version every five seconds to reload themselves. It works and the helper is local, so the cost is small. But two mechanisms for "something changed" is one more than needed, and the one-second scoreboard poll is why the control page can lag a Stream Deck press by up to a second.

Recommend
After D1, publish the board on the same socket as a second message type, and let the scoreboard, control page, goals and countdown subscribe instead of polling. Keep the HTTP endpoints for OBS sources and the plugin.
Alternative
Leave polling. It is simple and well understood. Choose this unless D1 is done and the lag is noticed.

Design

D8

Render the tab bar from one place

Medium

Finding. The Studio tab bar is pasted into eight pages. The links are in the same order in all eight, which is good, and yesterday's rename of the Graphics tab to Docs is the proof of the cost: an eight-file PR for one word. Pages with a Stream Deck or Docs link elsewhere also repeat those links in slightly different ways.

Recommend
A twenty-line studio-bar.js that renders the bar and marks the current tab, like fit.js does for graphics. Each page keeps a <header class="fp-bar"> placeholder for the no-script case. The Go menu in the Mac app could read the same list.
Risk
None.
D10

One convention for where a graphic's styles live

Low

Finding. Two conventions coexist. Twenty graphics put their styles in the shared graphics.css (438 lines of .card, .fixture, .ladderbar, .worm and so on, one block per page). Eleven others carry their own styles inline (The Clash, winner, streaks, super shot, lower third, title, branding, intro and outro, logo, ad, goals), and two have a sheet of their own (scoreboard, ladder). All of them take their colours from the generated theme.css, so the competition look is consistent. What drifts is the chrome: panel radius, shadow, opacity and padding are set in each place, and a change to the house panel style means finding them all.

Recommend
Decide the rule and write it in the README: shared tokens and the panel primitive (radius, shadow, panel colour and opacity, title tab) in a small graphics.css, and each page's own layout in that page. That means moving the per-page blocks out of graphics.css into their pages, not the other way, so the shared file shrinks to what is actually shared. Do it one page at a time alongside other changes, checking each against the example PNGs.
Alternative
Leave it. The look is consistent today because the colours are; only future panel changes pay the cost.

UX

D5

A health strip on the Output page

Medium

Finding. Studio is good at hiding problems from the stream, and that means problems hide from you too. On a night, the questions are: is PlayHQ answering, how old is the last reading, which game is being followed, is the clock following the scorer, are the outputs on and the Stream Deck connected. Today those answers are spread over the control page, the menu bar status and the log. The Output page, which stays open all night, shows none of them.

Recommend
One line at the top of the Output page: the game being followed, "PlayHQ read 4 s ago" (amber past twice the refresh, red with the last error after a minute), clock mode, outputs on, and a link to the log. The same data in /api/version or a small /api/health so the Stream Deck plugin can colour a key with it later.
Risk
None; it only reads what the board already records (playhqError, playhqSeen, playhqWaiting).
D12

Finish the renames

Low

Finding. The product has been renamed twice and the user-facing names are now consistent: FirstPass Studio, on air and off air, Scene View, Sources, Scenes, Sequences, the Docs tab. Underneath, the old names remain where a person can still meet them: the log file is playhq-graphics.log, the helper prints "PlayHQ Graphics is running", the log source for pages is "helper", the README and a few comments still say "helper" and "home page", and index.html redirects to the Docs page. None of this breaks anything. It does cost a new reader a few minutes working out that three names mean one thing.

Recommend
A glossary at the top of the README (Studio, the helper, the scene, a source, a scene, a sequence, the data folder) and a tidy of the console messages. Leave the log file name alone unless a migration is being written anyway; renaming it is not worth a data step.
D14

A module map and a stream night checklist

Low

Finding. The README is thorough about features and settings, and each module explains itself at the top. What is missing is the page in between: one screen that says which file owns what, how a request flows from a page to PlayHQ, and what runs on a timer. Reviewing this repository meant rebuilding that map from the code. Separately, the operational knowledge for a night (what to open, what to check, what to do when PlayHQ stops answering, how to go manual) lives in Matt's head and in thread history.

Recommend
docs/ARCHITECTURE.md, one page, kept current by the same rule as the Docs page. And a "Before you go on air" checklist on the Docs page, which D5 can link to when something is amber.

If all of it is approved, this order

Each line is one pull request. The first three change behaviour and are the ones that protect a stream; the rest are moves that make the code easier to keep changing.

  1. D2 atomic writes, then D4 the port message. Tiny, no decisions inside them.
  2. D1 the helper's own PlayHQ timer. Test on a real night with the scoreboard hidden for a break.
  3. D3 network access, once the CORS and toggle choice is made.
  4. D5 the health strip, which D1 makes truthful.
  5. D8 the tab bar and D7 the page list. Both remove a "remember to also edit" rule.
  6. D6 and D9 module splits, one module per PR, between feature work.
  7. D13, D12, D14, D10 and D11 as housekeeping when convenient.

Not recommended: a framework, a bundler, TypeScript for the helper, a database, or moving to a cloud service. The current shape is the right one for a tool that must start on a Mac in a sports hall with no internet beyond PlayHQ.
