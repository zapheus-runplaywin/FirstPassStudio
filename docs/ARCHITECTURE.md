# How FirstPass Studio is put together

One page on which file owns what, how a request travels from a graphic to PlayHQ, and what runs on a timer. The
README says what Studio does and how to use it; this says how it is built. Keep it current the way the user guide is
kept current: a new module, timer or data flow gets its line here in the same pull request.

## The three parts

```
 Mac app (desktop/)  ──starts──▶  the helper (server.ts + modules)  ──HTTP──▶  PlayHQ
   menu bar, windows,               serves the pages, the API and         api.playhq.com (GraphQL)
   display/NDI/DeckLink outputs     the scene; saves the data folder      spectator.playhq.com (live feed)
         │                                   ▲
         │ shows                             │ fetch + WebSocket
         ▼                                   │
 the pages (public/)  ◀──────────────────────┘
   Studio pages you work in, and the graphics that go on screen
```

- **The Mac app** (`desktop/main.ts`) is an Electron menu bar app. It starts `server.ts` as a child process when a
  Studio window opens ("on air"), stops it when the last window closes, and owns the outputs that need the Mac:
  full-screen displays (`desktop/outputs.ts`), NDI (`desktop/ndi.ts`), Blackmagic (`desktop/decklink.ts`, with its sound in the SDI heard from its window by `desktop/soundtap.ts`), an output's sound sent to the Mac's sound outputs by name (`desktop/soundcopy.ts`, a hidden `scene.html?copy=1` window per named destination in Sound goes to), the video outputs fed
  by an off-screen render of the scene (`desktop/scenewindow.ts`; at 2160p it's 1920 x 1080 points at twice the density). `desktop/perf.ts` measures each output's CPU, memory and frame
  rate every 5 s while one is showing; `outputs.ts` shows it on the Output page and logs it once a minute. `desktop/windows.ts` makes the app's own windows
  and menus from the tab list in `public/studiobar.ts` (and the page zoom: one level for every Studio window, kept as `pageZoom`, shown in the View menu, told to each page as a `studio-zoom` event for the bar's chip, which asks for 100% with `#zoom=100`); `desktop/updates.ts` and `desktop/whatsnew.ts` handle updates.
- **The helper** is plain Node, no framework: `server.ts` routes every request by hand and the modules beside it each
  own one subject. Code shared with the other FirstPass products comes from FirstPass's own packages (`@firstpass/*`,
  TypeScript in this repository's `packages/`, an npm workspace that `npm run build` compiles to each package's `dist/` before
  Studio itself, and published to npm for Vantage and HQ by `.github/workflows/publish-packages.yml` when main has a version npm
  doesn't); so far that is `@firstpass/playhq`. Everything it saves goes in the data folder (`datadir.ts`), never inside the app.
- **TypeScript:** the helper and the Mac app are TypeScript in strict mode (`tsconfig.json`), compiled by `npm run build` into `out/` (CommonJS,
  the Mac app's `desktop/*.ts` into `out/desktop/`, beside the HTML pages and icons that stay in `desktop/`), which is what runs and what the app packs; `appdir.ts`
  finds the app folder (`public/`, `vendor/`, `native/`, `config.json`) one above `out/`. `playhq.js` stays JavaScript for now,
  typed by `playhq.d.ts`. What comes from outside (a request's body, a saved file, PlayHQ's answers, the messages between the Mac app and the helper) is
  `unknown` until it is checked with `check.ts` (`obj`, `arr`, `str`, `num`); the types the modules share are in `types.ts`. An
  `any` needs a comment starting `any:` saying why, and `test/typescript-any.test.js` fails on one without it. The pages' scripts are
  TypeScript too: `public/tsconfig.json` compiles `public/*.ts` and `public/output/tsconfig.json` the Output page's parts into `out/public/`,
  which Studio serves before `public/`, so a page's script tags name `.js` as before. The shared scripts (`studio.ts`, `asktext.ts`…)
  are plain scripts that share the page's scope; a page's own script (`planner.ts` for `planner.html`, `worm.ts` for the score worm graphic) is a module, loaded with
  `<script type="module">`, so its names stay its own; the Output page's parts share one scope of their own. `public/view.d.ts` types
  what Studio answers more than one page (the scene, the outputs, `/api/health`, `/api/scoreboard`, `/api/teams`); an answer only one page reads is typed in that page's script.
- **The user guide** (`docs/user-guide/index.html` and its `img/` pictures) is packed into the app and served at `/guide/` by `server.ts` (`sendGuide`, with Studio's own Montserrat in place of Google's, so it reads offline); Help > FirstPass Studio User Guide and User guide in the menu bar icon open it in a window of its own (`windows.openGuide`).
- **The Remote** (`public/remote.html`) is a phone page on its own, without the bar: the Output page's status from `/api/health`, the scene from `/api/scene/events`, and Play next, Skip, the sequence playing's buttons and a key per sequence through `POST /api/scene`, so a phone pairs with Allow everything; while the board is on Manual, score, clock and quarter keys through `POST /api/scoreboard` (scoring-only phones too).
- **The Commentator mic** (`public/commentator.html`) is a phone page too, opened by the Secure phone link (a phone gives a page the mic only over https): it sends the phone's mic to Output 1's window over WebRTC through `phonemic.ts` (`/api/phonemic/...`) and plays back what that window sends on the same connection (its program without the mics, plus every other mic: a mix-minus built in `scene.html`, where every window that plays sound plays its music and video players through one Web Audio mixer on its device, which the board's Sound out meter and the phone hear, so nothing is copied per song), keeps the screen awake, and starts again by itself when the connection drops; any paired phone may use it.
- **The pages** are static HTML in `public/`. The Studio pages (Output, Production Planner, Scoreboard control, Recordings, Socials,
  Competitions setup, Sponsors, Athletes, Devices, Docs; the keyboard order, ⌘1 to ⌘0; the bar shows them grouped Run, Plan, Set up, Docs apart,
  with status chips from `/api/health`; on a phone, a touch screen up to 700 px wide, the bar is just the phone pages
  Socials, Remote and Commentator, with no chips, and `/` opens Socials) share `studio.css` and `studiobar.js`: the page kit in `studio.css`
  (section, headings, buttons, segmented controls `.fp-seg`, switches `.fp-switch`, help text, dialogs, scoped with `:where(body.fp)` so a page's own classes win) is what each is built from, its `--fp-*` tokens carry the
  brand kit's light and dark values (`prefers-color-scheme`; the app pins the theme with `nativeTheme.themeSource` from the menu bar icon's Appearance),
  and a page's own `<style>` carries only what is really its own (`test/studio-kit.test.js` keeps it so). `studiobar.js` also gives any name cut short (an ellipsis or a line clamp) its full text as a tooltip on hover (`data-full` when the element holds more than the name). Each page has one line under its title and a **More in the guide** link to its part of the user guide (`/guide/#s3-3` and so on), where the longer explanations live; the Docs tab is the guide itself, served by `sendGuide` with Studio's bar on top. The graphics only talk to the helper
  on this computer and keep the competition's own look.

Two more pieces live in the repository: the Stream Deck plugin (`plugins/studio-deck`, TypeScript, talks to the helper's
`/deck/*` links and follows the scene's and the switcher's SSE feeds, `/api/scene/events` and `/api/switcher/events`) and the native addons for NDI and DeckLink (`native/`).

## Module map (helper)

| File | Owns |
| --- | --- |
| `server.ts` | Routing, the competition in use and `control.json`, health and page version, start-up and shutdown. |
| `teams.ts` | The team sheets (`/api/teams`: teamlist, match ups, commentator stats) and each player's shooting stats, from PlayHQ's game page line ups with the live feed's team totals, or with a Client ID its REST Summary for the Game; which way round PlayHQ's teams and line ups sit against the scoreboard (`orientToBoard`); whether scoring has opened (`scoringState`); the team list warm up when a game is picked (`warmTeamLists`); `positionOf`. |
| `lowerthird.ts` | The person lower third (`/api/lowerthird`): an athlete from the register by name with their team, club logo and photo, and the athletes the Output page suggests for it (`/api/lowerthird/athletes`). Its bar's look is `public/lowerthird.css`, shared with `commentators.html`'s Lower thirds look (a bar for each commentator on the mic). |
| `playhq.js` | Everything that talks to PlayHQ, on FirstPass's shared PlayHQ package `@firstpass/playhq` (`packages/playhq` in this repository, published to npm, where Vantage and HQ install the same one): the package asks and reads (the guest session, the queries, the parsers for competitions and seasons, ladders, rounds and games, one game in detail and the live feed), and `playhq.js` keeps what is Studio's own: how long each answer is kept and the last good one while PlayHQ fails (`createKeeper`), team logos, the competition and season from the setup page, the scoring window, per game when the live feed last answered, said "not electronically scored" and changed (`liveSeenFor`), the game cache, and the hooks for the traffic counter and debug log (`onRequest`), the recording (`onAnswer`) and practice games (`answer`). |
| `playhqnet.ts` | What talking to PlayHQ costs: every PlayHQ request (`playhq.js`, `teams.ts`) calls `note()` (time and answer size) or `failed()`; `snapshot()` gives the ping, the last minute's bytes a second and the total since on air, for `/api/health` `playhq.net` and the Output page status board's PlayHQ line. |
| `athletes.ts` | Team logos, athlete photos (on graphics only once the athlete has approved their use, `photoOk`), the athlete register (`athletes.json`), what the athletes page shows and edits, a team's season squad for short line ups. |
| `games.ts` | The games: which game night and round are "this round", the fixture, up next and the end of night card, intro and outro, the countdown, automatic game selection, the season graphics (ladder bar, head to head, form, ticker, top shooters) and the finals. |
| `planner.ts` | The Production Planner (`planner.html`): the commentator pool (with each one's headshot in `headshots/`, for the Socials Commentary team picture, the fixture board and the commentators' lower thirds) and each game night's court and commentators (`planner.json` in the competition's folder), nights that take the plan of the night before, the court it hands automatic game selection (`courtFor`), who is on the mic for the game on the scoreboard (`/api/planner/onair`, for the commentators graphics, with the game's assigned saved run order, which `server.ts` `plannerRunOrder()` loads once as the scoreboard moves to the game) and the night's whole fixture with live scores (`/api/planner/fixtureboard`, for `fixtureboard.html`). |
| `socials.ts` | The Socials tab (`socials.html`): a game night's pictures for social media (`social.html` at Instagram's square, portrait and Story sizes), Upcoming and Results, from the fixture and results, the ladders (with each team's place before the night, `placesBefore`, for ladder movers and Round in review's upsets), the night's and the tournament's shooting so far (`games.tallyShooters`), the Production Planner, each division's finals (`games.getFinals`, for Finals bound, the Finals draw, Champions and the finals' names on a finals night), the sponsors and logos; the sponsor strip, Studio mark and PIVT logo choices, the colour sets (made from the competition's colours with `competitions.colourVars`, or by hand), the picture sets (which kinds of picture the tab lists, named in `KIND_NAMES`), the template sets (`TEMPLATES`; their styles in `public/social-templates.css`, their faces in `fonts.ts` `TEMPLATE_FONTS`) (`socials.json` in the competition's folder); polaroid photos (`socials-photos/` in the local folder); and saving, which it asks the Mac app to do over the message port (`desktop/socials.ts` draws each picture off screen and saves the PNGs in Pictures/FirstPass Studio, then opens the folder or the Share menu; saved for a phone, `toDevice`, they're made in a temporary folder, nothing opens, and the phone fetches them from `/api/socials/made/<id>/<n>` for an hour). |
| `socialstats.ts` | What the Socials pictures work out from the season's fixture, results and ladders, asking PlayHQ nothing: each team's place before a night (ladder movers, Round in review's upsets), Form guide, Round preview, Byes, Finals race, Countdown and Season draw; Night in numbers, Club round up, On a roll, the Team season card and the Season wrap's biggest win. Team super shots adds up each game's team counts (`socials.ts` `teamSupers()`, `teamTotals()`). The shooting pictures (Sharpshooter, Super shot leaders, On fire, the season card's and Season wrap's shooters) are in `socials.ts`, from `games.tallyShooters`. The hand picks (Player of the match, Team of the round) read the line ups with `games.readLineups`; Athlete spotlight uses `athletes.ts` `spotlight()`; Sponsor spotlight's time on screen is `exposure.report()`. Game story and Score worm come from `board.ts` `gameStory()`: the board keeps each streamed game's Game stats and Score worm in `game-stories/` (local folder, through `stories.ts`) as it goes, at once when the game ends or another is picked, and the same for each of the night's other games it follows in the background (marked `followed`); `stories.ts` also copies in the finished stories other Studio Macs kept (and puts this Mac's own finished ones in iCloud Drive, `toCloud()`, including a game left part way when Studio was quit), keeping the better of two (`better()`: fewer gaps, then streamed over followed), and filling one's gaps from the other where it saw those goals (`board.ts` `mergeStories()`, over the `goalOrder` each story keeps, handed to `stories.ts` with `useMerge()`; the stats, worm and moments are worked out again, and the story says whose stories `filled` it). Moments of the game is the story's moments (the board keeps every moment of the game in `gameMoments`). Game stats, Shooting duel's team line and Night in numbers' super shots use each team's own counts from `games.readLineups` (`totals`; `socials.ts` `teamTotals()`, the players added up only when PlayHQ has none), since PlayHQ can give a goal to a team without a player; Team sheet is `athletes.ts` `teamSheet()`; Head to head is the Form guide's meetings. Runs of the night, Super shot time (the worm's `superShot.byPeriod`) and Comeback of the night are `socials.ts` `ofTheNight()` over the night's stories. Watch it back's QR code is `sponsors.qrSvg`. Milestones come from `athletes.ts` `milestones()` (games played from the register's records and the season's line ups). |
| `stories.ts` | Each streamed game's story (`game-stories/` in the local folder), kept by the board, and shared between Studio Macs so the Socials tab on either has every court's games: each Studio announces itself with Bonjour (`dns-sd -R`/`-B`, `_firstpass-studio._tcp`), lists its own finished stories at `GET /api/stories` (read only, so no pairing) and copies the others' every 3 minutes; finished stories also go to `iCloud Drive/FirstPass Studio/game-stories/` when iCloud Drive is on, copied in by the other Macs. A copy carries `from` (studio, network or icloud), never replaces the Mac's own story and replaces another copy only when newer. |
| `board.ts` | The board: scores, clock and period by hand or following PlayHQ's live feed, the goal order, super shots, hot streaks and moments, the game stats card and the score worm; whether PlayHQ is really scoring the game live (`playhqTrouble`: the feed says it isn't scored while the game is under way, or nothing new for 4 minutes while the scorer's clock runs; from `playhq.js` `liveSeenFor`); back to Follow PlayHQ from a hand score, keeping it while PlayHQ is behind and its feed unchanged (`holdHandScore`, `followHold`); a reading that is PlayHQ catching up, noted as a gap with no goals, super shots or moments (`catchUpIn`); a gap in a game still on filled from another Studio Mac's story of it so far (`fillFromPeers` every 30 s while there is one, through `stories.ts` `liveFrom` and `mergeStories`, its streaks marked fired so nothing replays on air; `keepOwedStories` keeps each story no more than 15 s behind); the night's other games followed in the background (`followGames`, `refreshFollowed`: each on a board of its own that no page shows, through the same goal order, quarters, clock and moments, with nothing played on air; `takeOver` and `handOn` pass a game's goals between them and the scoreboard; a failed read backs off; `followed-games.json`); `scoreboard-state.json` and the lasting settings in `control.json`. |
| `competitions.ts` | Saved competition setups in `competitions/`, `active.json`, templates import, per-club logos and colours. |
| `scene.ts` | The scene: sources as layers on one frame, each on or off per output (`visible` for the primary, `out` for the others), scenes (saved sets of sources, shared by the outputs, with a current scene per output), the Output page's state, the WebSocket and SSE feeds that push it to pages and the plugin, game triggers. |
| `sequences.ts` | Sequences: steps played in order, waits, repeats, Stream Deck key, time left. Sequences are shared by the outputs and play on the one picked, or together on all of their `playsOn` outputs (automatic starts too), with one runner per output (`within()` switches between them) and a Then per output (`thenOn`); a sequence's music is Output 1's: its runner plays, quiets and stops it (`sound()`), and the other outputs' runners play without it. The run order: Output 1's queue of sequences and scenes (`queue`, empty on the other outputs; `ro*` actions always act on Output 1, saved as `runOrder` and named `runOrders` in `sequences.json`); `finish()` plays its head before the Then, `start()` takes the head as it starts (onto `played`, tonight's list of what the run order has played, not saved), `trigger()` moves its sequence to the head on Output 1, `/deck/runorder/*` and the `ro*` actions (`roRename` keeps a saved order's id; `roLoad` with `planner` sets `runOrderNotice` when it drops queued items). |
| `music.ts` | The stream's music: one player, playlists, fades and ducking, the super shot song, and `tail`, the song fading out under a sequence's new music (a crossfade). All of it is Output 1's: Output 1's windows play it, the other outputs' play without it. |
| `mics.ts` | Live mics plugged into the Mac (`mics.json`, one set per Mac): each mic's input, channel, level, mute and low cut, the master level and mute, and the ducks under music, a video's sound, scenes that duck the music and by hand (called duck on screen, as on the music; the settings keys, actions and ids keep their old name, dip, and `/deck/mics/dip` still works beside `/deck/mics/duck`) (worked out in `state()`, which `scene.ts` calls). The mics are Output 1's: its own window (`scene.html?fit=1`) opens the devices with Web Audio, mixes them in through a limiter and reports what it hears twice a second (`/api/scene/mics/report`, by window; a sound copy of Output 1 mixes the mics ticked for it); the Output page reads them together from `/api/scene/mics/live`. A Scene View never opens them. A mic plugged into the switcher instead (`on: 'atem'`, one of its Fairlight mic or line inputs, or half of one split in two) is mixed by the switcher: `mics.ts` moves its fader through `switcher.ts` (`micInputs()`, `setMicFader()`), stepping every 50 ms while a duck fades, takes the faders as it finds them on connecting (sends nothing), and a fader moved on the switcher becomes the mic's level. Its meter comes from the Fairlight levels `switcher.ts` asks the switcher for on connecting (`micLevel()`, the loudest over the last half second), shown with a mark for its fader. `live()` also says which mics have heard nothing above -55 dBFS for 10 s while their readings keep coming (`silent`, seconds by mic id; never a muted mic), for the card and the board's Mics line. |
| `sponsors.ts`, `exposure.ts` | Sponsors, spots on the graphics, ads in sequences; proof of play for the exposure report. |
| `viewers.ts` | Live viewer numbers from YouTube and Facebook while a video output is on. |
| `recorder.ts` | The game recordings: one gzipped JSON-lines file per PlayHQ game on air in `Recordings/` (local data folder), from when the board's game is due (`games.ts` `leadMs()` before its start) to `afterMinutes` after PlayHQ says it's finished, the next game or off air, starting with the last of each answer already known; fed by `playhq.js` (`record.playhq`, `record.live`), `board.ts` (`record.action`), `scene.ts` (`record.scene`, `record.board`) and `server.ts` `send()` (`record.answer`, a graphic's reads). Written every 5 s as its own gzip member; tidied at start (no game, or older than 60 days). `/api/recordings`. Each game followed in the background (`board.ts` `followedGames`, fed by `server.ts` each second to `followGames`) gets its own "(followed)" recording from its first reading to `afterMinutes` after it's done: the same `playhq` lines and its own `live` lines, nothing that went to air, its game line marked `followed` with its date and time. |
| `replay.ts` | 4K replay: a recording's on-air layer (scene, board, a graphic's reads) back on the pages through `scene.ts` `replay()`/`replayBoard()` and `server.ts` (recorded answers for graphics, changes refused with 409 while it runs). Play, Pause, nudge, seek, Stop and Follow at `/api/replay`; the offset to a followed HyperDeck's timecode per recording in `replay.json`. |
| `hyperdeck.ts` | Reads a HyperDeck's transport and timecode over its Ethernet control protocol (TCP 9993) while a replay follows it. Read only: it never sends a command that changes the deck. |
| `sditimecode.ts` | The timecode coming into the UltraStudio's SDI input, read by the Mac app (`desktop/decklink.ts` `readInput`, `native/decklink` `inputStart`) and sent to the helper while a replay follows it; tells playing from stopped. |
| `practice.ts` | Practice and demo games: a recording's game played back as if live; a demo game wears a finished game's teams and athletes from the competition in use (`dress()`, `wear()`). `playhq.js` asks it (`answer()`, `live()`) instead of PlayHQ while one runs; answers are moved to now (`shift()`). Keeps and restores the scoreboard (`board.ts` `snapshot`/`restore`), holds exposure and pauses the recorder. `/api/practice`; `/api/playback` (server.ts) answers it and the replay together, for the tab bar's strip and the plugin's Replay keys. A followed game's recording plays the same way, asking PlayHQ for what it doesn't have; each quarter's jump is when the scorer started its clock, and `nudge(ms)` (`/deck/practice/nudge/<ms>`) lines it up with a video. |
| `outputs.ts` | Up to four outputs, each with its own route (display, chroma, fill+key, NDI, Blackmagic) and on/off; the first is the primary, the only one with the music and mics. Each has its sound destinations (`sound`: `own` is the SDI of a Blackmagic output or the Mac's sound output, `mac` the Mac's sound output as well, or a Mac sound output by name with the mics ticked for it; `windowsOf()` mutes the window with no destination of its own, `copies()` lists the named ones for the app, `soundState()` how each is doing, and `soundLive()` each one's level and sample rate for the board's Sound out, from the windows' `POST /api/outputs/level` and the app's SDI capture, read with `GET /api/outputs/sound`). Earlier outputs keep a display, the Blackmagic device or an NDI name. The app does the showing. The picture (`quality`, HD or 4K) is one setting for every output: in 4K the NDI and Blackmagic outputs send the 2160p version of their saved 1080p format (density 2), worked out each time, so the saved formats never change; in 4K a Blackmagic output can also have the device's own 2160p format picked, sent as it is (in HD, the 1080p one at its rate). Each output also keeps how it comes into the ATEM (its key and switcher inputs), given to `switcher.ts` by `switcherPlan()`. |
| `switcher.ts` | The Blackmagic ATEM switcher, if one is set up: finding it (Bonjour via macOS's `dns-sd`), one connection through `atem-connection` (in-process, UDP 9910), its state for the Output page and the plugin's Switcher keys (`/api/switcher/events`, sent on each change), and the cuts, previews and keys the Output page and `/deck/switcher/*` ask for; `switcher.json`. Sends nothing by itself. Also cleans and runs the switcher actions saved on sequence steps and scenes (`run(actions, why, owner)`, `cancel(owner)`): `sequences.ts` and `scene.ts` call it for the primary output only. Stinger cuts: it plays the scene's stinger through `scene.ts` (`stingerSource`, `playStinger`), and `stinger.html` says when it covers the frame (postMessage to `scene.html`, which posts `stingerStarted` to `/api/switcher`), so the cut is timed from the page's own settings plus the line-up. The stinger plays on the output on a downstream key (`stingerOutput()`, Output 1 unless another one that's switched on is), each output has its own line-up (`lineups` in `switcher.json`), and only that output's windows' report counts. Each output's key (`keyChecks`, in its status as `keys`): reads the key an output comes into (`outputs.switcherPlan()`: its Into the switcher as, inputs and signal) and lists what differs; `keySetup` writes only that, when the Output page asks. Cameras per output: `take()` puts the paired upstream keys that must change in the next transition selection for Studio's cuts, autos and stinger cuts (and restores it), and Keys follow the camera (`followSoon`) sets them after a program change made elsewhere. |
| `finals.ts`, `fonts.ts` | Finals formats per competition and division; the fonts a competition can use. |
| `datadir.ts`, `datalocation.ts`, `migrations.ts`, `savefile.ts` | Where settings live, moving them to iCloud Drive, bringing old settings up to date after an update, writing files atomically. |
| `devices.ts` | What may change things from another device (the Devices… window, `devices.json` on this Mac only): This Mac's links and named link sets, each with a key that Make a new key replaces (picked on the Output and Stream Deck pages by `public/linksets.ts`), programs that asked to pair (`/api/pair`) and were allowed in the Mac app's dialog (`desktop/main.ts` askToPair), phones and browsers, which pair from `public/pair.html` (`?then=` goes on to a page afterwards, the QR code of `/api/phone-link` in `server.ts`) and get a device cookie with a level (scoring or full; `access.scoring()`), and Studio plugins, which pair with a public key and sign each press (`signed()`; the plugin's side is `plugins/studio-deck/src/lib/identity.ts`). |
| `phonemic.ts` | A phone as a backup commentator mic: passes WebRTC offers and answers between the Commentator page (`public/commentator.html`, a paired phone) and Output 1's window (`public/scene.html`, which mixes the phone like a Mac input); adds the phone's mic (`mics.ts`, `on: 'phone'`) on its first offer. |
| `securelink.ts` | The secure phone link (Devices tab, off until set up): this Mac's own name in the Route 53 zone it's given (PIVT's is `studio.firstpass.pivt.au`, its name read from the zone), pointed at its LAN address in Route 53 (`route53.ts`, signed requests with Node's crypto) with a Let's Encrypt certificate (`acme.ts`, ACME DNS-01 and a hand-built certificate request), served on https (port 8443) by `server.ts`'s same request handler; `/api/phone-link` gives its link when ready. At launch a saved certificate still good is served at once, and Route 53 is sent the address only when it has changed (not waited for). `securelink.json` in the local data folder; the key's secret in the Keychain. |
| `access.ts` | Who on the network may change things (the "Only this Mac can change things" switch, ticked at every launch), and who may press a Stream Deck link (its key, the plugin's header, or Studio's own pages). |
| `linkhost.ts`, `zip.ts`, `examples.ts` | The `.local` name in links; just enough zip for export and backup; example PNGs of every graphic. |
| `appdir.ts`, `check.ts`, `errors.ts`, `types.ts`, `playhq.d.ts` | The app folder above `out/` and the version (`appdir.ts`); reading outside data that came in as `unknown` (`check.ts`: `obj`, `arr`, `str`, `num`, `own`); an error's message and stack from anything thrown (`errors.ts`); the types the modules share (`types.ts`: the log, a request's query and body, `send`, `config.json` and `control.json`); `playhq.js`'s types until it is TypeScript itself (`playhq.d.ts`). |

## How a request flows

1. A graphic such as `scoreboard.html` asks the helper, for example `GET /api/scoreboard`. Pages never call PlayHQ.
2. `server.ts` checks `access.ts` (writes from another device may be refused), then routes the path.
3. For PlayHQ data it goes through a cache per query. A reading younger than its max age is answered from memory;
   otherwise one call goes to PlayHQ and every page asking at the same moment shares it. Fixtures, ladders, rounds and
   `discoverGame` use `api.playhq.com/graphql` with a guest cookie; the running score, clock and quarter come from
   `spectator.playhq.com/graphql`.
4. The live feed is read only from "electronic scoring starts N minutes before the game" (competition setup), and only
   often while the game is played (`playhq.js` "Being kind to PlayHQ"): at **Check PlayHQ every** from 2 minutes before
   the start until 2 minutes after PlayHQ finishes it (or whenever the feed says it's under way), every 30 s before
   that, every 5 minutes after it. "Not electronically scored" is logged once per game and kept as long as a reading.
   Fixtures, ladders and game pages are kept as their caller asks while any game is on, at least 5 minutes when none
   is; `/api/games?fresh=1` (Refresh list) reads afresh (`askAgain`).
5. Scores, the clock and manual overrides live on the board in memory and are saved to `scoreboard-state.json` so a
   restart picks up where it was.
6. Anything that changes the scene (a source on or off, a scene or sequence starting) goes through `scene.ts`, which
   pushes the whole scene to every page holding the WebSocket at `/api/scene/socket` and to the plugin's SSE feed.
7. The scoreboard travels the same socket as a second message type: a page that sends `{"subscribe":"board"}` gets
   what `GET /api/scoreboard` gives, at once and on every change (`scene.publishBoard`, called from `saveBoards` and
   each second). The ATEM switcher's state (`switcher.ts`) travels it a third way, for a page that sends `{"subscribe":"switcher"}` (the Output page), on each change, and to the plugin's Switcher keys over its own SSE feed (`/api/switcher/events`). `sceneevents.js` wraps them for the pages; the HTTP endpoints stay for the plugin and other tools.

Every change to a saved file uses `savefile.ts` (write to a temporary file, then rename), so a crash mid-write never
leaves a half-written settings file. Its async saves of one file go one at a time (the newest waiting one is written
next), so saves started close together can't land out of order and leave older contents on disk. When Studio stops,
`flushSync()` (run on process exit in `server.ts`) writes any save still in the background, so the last change before
going off air is kept. A background save whose rename has already been asked of the operating system can't be called
back and could finish after that write, putting older contents back (PR #467: the scoreboard's clock returning at 10:00
after a restart); so `flushSync()` first removes that save's temporary file (`renaming`), and the late rename fails
harmlessly or had already happened and is written over.

## What runs on a timer

| Where | Every | Does |
| --- | --- | --- |
| `server.ts` refreshTick | 1 s | Refreshes the board from PlayHQ when the last reading is older than the game's pace (`playhq.js` liveAge): **Check PlayHQ every** (control page, default 5 s) from 2 minutes before the start until 2 minutes after PlayHQ finishes it, 30 s from scoring opening until then, 5 minutes otherwise; nothing before scoring opens. Runs whatever windows are open (review decision D1). |
| `server.ts` followNight | 15 s | The game night's games (`games.getCurrentGames`, PlayHQ's fixture through its cache) to `board.followGames`, so the night's other games are followed in the background (Scoreboard control's **Also follow the night's other games**). Not during a practice game. |
| `server.ts` refreshFollowed | 1 s | Reads each followed game due a reading, at the same pace as the board (`playhq.js` liveAge), once its scoring has opened, until PlayHQ says it's finished; a failed read waits 10 s, doubling to 5 minutes. |
| `server.ts` autoPick | 15 s (first after 3 s) | Game auto-select: sets tonight's court when a game night arrives (the Production Planner's, else the competition's fallback court; a court changed by hand lasts that night; a court name typed for the graphics is cleared too), then picks the next game on it when its scoring window opens. |
| `server.ts` scene.game | 1 s | Hands the game snapshot to the scene for game triggers (quarter breaks, full time) and the super shot song. |
| `viewers.ts` | 30 s per stream | Live viewer counts, only while a video output is on. |
| `switcher.ts` (atem-connection) | about 2 per second each way | The switcher's own heartbeat while connected; after about 5 s of silence it counts as lost and the library reconnects every second. A switcher found by name is looked for again every 15 s while lost, in case its address changed. |
| `scene.ts` SSE ping | 25 s | Keeps the plugin's event stream open. |
| `scene.html` mics | 25 ms, 500 ms | In the primary output's window, while mics are set up: the mics' levels follow the settings and the duck; twice a second it reports their levels and trouble to the helper. The Output page reads that twice a second while its Mics section is open. |
| `server.ts` pushBoard | on each save, and 1 s | Pushes the scoreboard to the pages following it over the scene socket (scoreboard, control page, goals, countdown) when it has changed. |
| Pages | 1-30 s | Ticker, super shot, streak and commentator stats pages poll the helper only (see "Data and bandwidth" in the user guide's Reference). |

Logging: one debug log, `logs/playhq-graphics.log` in the data folder (15 MB cap), written by the helper and by pages
through `/api/log`. The log file keeps its old name on purpose.

## Tests

`npm test` runs the `node:test` suites in `test/`. `test/support/studio.js` starts a real Studio (`out/server.js`) on a free port
with its own data folder; `test/support/playhq.js` is a stand-in PlayHQ with a made-up season around today's date
(`world.fail` and `world.answers` make one request fail or answer oddly, for the PlayHQ outage tests). A
Chromium page-load test runs when a browser is available, and `test/app.test.js` runs the Mac app itself (Electron, on
Linux under `xvfb-run`, with Electron's binary from `node node_modules/electron/install.js`). The Tests workflow runs
them on every pull request and before each Mac app build; `test/packaging.test.js` checks that every module `out/server.js` and the app load is in the app's file list. `npm test` builds first (`pretest`), and the tests load the compiled modules from `out/`. Both workflows keep Electron's download (and the Mac build electron-builder's tools) in the Actions cache under their version, so a newer version is downloaded fresh, and try the download again for a few minutes when GitHub answers 504.
