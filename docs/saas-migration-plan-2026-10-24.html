FirstPass Studio · SaaS migration plan · 24 October 2026

From one Mac in the venue to a licensed cloud service

Studio today is a Mac menu bar app that runs a local Node helper, serves 42 graphics pages from public/, follows PlayHQ with a guest session, and keeps everything it knows in files under ~/Library/Application Support/FirstPass Studio. This plan says what has to change for other associations to pay for it and run it without Matt's Mac, in what order, and which choices only Matt can make. It builds on the architecture review (D1 to D14, all merged) and the security review (S1 to S7 merged; S8 and S9 were parked until licensing is real, and this plan is where they land).

Effort figures are weeks of focused work by one person with Claude, and they are estimates. Anything marked "to confirm" has not been tested against the real service.

Where Studio is today, in the terms that matter for a move

One tenant, no accountsNothing in the helper knows who is asking. access.js decides by network address and the "Let other devices change things" switch; the Stream Deck links /deck/* carry no token. Every setting is global to the one data folder.
State is filesactive.json, competitions/<id>/settings.json, scene.json, sequences.json, sponsors, athletes.json, scoreboard-state.json, control.json, plus folders of logos, photos, fonts, music and media. All writes go through savefile.js; datalocation.js already abstracts "where the folder is" (local or iCloud Drive) with a PROVIDERS table.
PlayHQ is read as a guestplayhq.js fetches a guest cookie from the public site, then uses api.playhq.com/graphql and spectator.playhq.com/graphql (the live score feed, found from Matt's own browser traffic). No partner key. One poller per competition, 5 s while a game is followed.
The Mac does the outputFull-screen displays, NDI, Blackmagic DeckLink and the loudness-levelled music all run in Electron on the Mac (desktop/scenewindow.js renders the scene off screen and hands frames to the outputs). OBS or vMix can also load any page as a browser source.
Real time is one WebSocketscene.js pushes the whole scene and the board to every page on /api/scene/socket, and an SSE feed to the Stream Deck plugin. Sequences, game triggers and music timing all run inside that one process.
Already modularD6 split the helper into playhq.js, board.js, games.js, athletes.js, each built by create(deps); D7 gave the pages one registry; 300 tests run against a real helper with a stand-in PlayHQ. The code is public under MIT.

Three shapes the product could take

The decision that drives everything else is where the graphics are rendered and where the state lives. The venue's encoder (OBS, vMix, a hardware switcher) must get the overlay from somewhere, and that somewhere decides whether a customer needs a Mac at all.

A. Licensed Mac appStudio stays as it is. Add sign-in, a licence check and payment; sell it like any desktop product. Cloud only holds accounts and licences. Cheapest to reach, no change to how stream night works, but every customer needs a Mac at the venue and Matt supports a fleet of installs.
B. Cloud control plane, local render agent Recommended
Settings, competitions, sponsors, athletes, the scene and its sequences live in the cloud and are edited in a browser. The graphics pages are served from the cloud, so OBS or vMix anywhere can load them. The Mac app shrinks to an optional "render agent" that signs in and provides displays, NDI, DeckLink and music. Customers without those outputs need no Mac.
C. Browser onlyLike B, but with no agent at all. Displays, NDI and DeckLink are dropped or replaced by a cloud-rendered video stream (expensive, adds latency, and NDI over the public internet is not a thing). Music would play in the browser. Loses the outputs Matt built this year.

B is the recommendation because it is C with Matt's existing outputs kept, and A is its first phase anyway. The phases below are written for B; stopping after Phase 0 gives A, and Phase 4 can be left out for customers who only use browser sources.

Everything the helper does today still runs, as the same modules, but once per tenant in the cloud instead of once on a Mac. The pages do not change much: they already talk to "the helper" by relative URL and follow the scene over a WebSocket. What changes is who is allowed to talk, where the files are, and where the frame comes from.

The phases

Each phase ships on its own and leaves Studio working for Thunder League as before. Phase 0 is worth doing even if nothing else happens.

Phase 0

Make the Mac app licensable

3 to 4 weeks

Studio keeps running exactly as now, but a copy can be sold to another association and supported from a distance. This is shape A, and it is the first step of shape B.

Build
  • Sign-in in the app (Apple, Google or email) and a licence record per organisation; the app checks it on start and once a day, and keeps working for 14 days offline. A tiny licence service (one table, one endpoint) is the first cloud component.
  • S8 from the security review: stream keys and the PlayHQ Client ID into the Keychain via Electron safeStorage; apiKey out of competition settings so a template never carries one.
  • Opt-in diagnostics: the existing debug log and a crash report uploaded with the customer's consent, because support can no longer mean "send me the log file".
  • A first-run experience for someone who is not Matt: pick a template, paste the PlayHQ link, see the Output page working. Every "Matt knows this" step on the Docs page becomes a prompt in the app.
  • Branding and legal: the binary ships under an end-user licence, not MIT (see M8); a privacy notice for the athlete register and photos.
Matt does
Chooses the identity provider (M3), writes the licence terms, sets up the Apple developer account for an App Store or notarised-only distribution, picks a price (M11).
Done when
A second Mac, signed in as a different organisation, runs its own competition from a template with no help from Matt, and the stream night checklist in the README holds for it.
Touches: desktop/main.js, desktop/windows.js, viewers.js (keys), competitions.js (apiKey), a new desktop/licence.js; a new small cloud repo for the licence service.
Phase 1

Accounts and settings in the cloud

4 to 6 weeks

The data folder becomes a tenant's row set in Postgres plus a bucket of files. The Mac app still runs the helper, but it reads and writes its settings through a storage interface that can point at the local folder or at the cloud.

Build
  • A store interface behind datadir.js and savefile.js: readJson, writeJson, list, readFile, writeFile, remove, with the local folder as the first implementation and Postgres plus object storage as the second. datalocation.js's PROVIDERS idea is the seed of this.
  • The tenancy model: organisation → members (owner, operator, viewer) → competitions. A competition setup, its sponsors, athletes, scene and sequences belong to the organisation; control.json and scoreboard-state.json stay per running instance.
  • Import of a backup zip (the Settings backup from PR #205) as the migration path for Thunder League and for any Phase 0 customer: the zip format is already the whole data folder.
  • Uploads get quotas and a virus scan (S9); the image signature checks from S3 already run.
  • Row-level security so one organisation can never read another's rows, tested the way test/access.test.js tests the switch today.
Matt does
Picks the stack (M4): Supabase is the recommendation because FirstPass HQ and the planned Vantage Phase 3 already use it, so one Auth and one Postgres can serve the family. Confirms the region (M5).
Done when
Thunder League's settings live in the cloud, the Mac app runs from them, and a second organisation's settings are invisible to it.
Touches: datadir.js, datalocation.js, savefile.js, every module that reads or writes a settings file (about 17 write sites after D2), migrations.js (data version 3: "in the cloud").
Phase 2

Graphics served from the cloud

4 to 6 weeks

The helper runs in the cloud, one instance per organisation (or per live competition), and the graphics pages come from a tenant address with an unguessable token in the link. OBS or vMix anywhere loads them. This is the phase that lets AMMNA or Netball WA stream without a Mac.

Build
  • Run server.js as a container with the cloud store; a small supervisor starts one per organisation on demand and stops it an hour after the last page or agent disconnects (a competition is live about 4 hours a week, so always-on would waste most of the bill).
  • Authentication (S9): browser sessions for Studio pages; a long random token in each graphics link, revocable from the Output page, because an encoder cannot sign in; per-user API tokens for the Stream Deck plugin.
  • access.js becomes the auth middleware: who the request is for (tenant), who it is from (member or token), what it may do (the changes() and privateRead() split already drawn in S1 and S2).
  • PlayHQ polling moves into one shared worker: a competition followed by two organisations (Thunder League on the association's account and on a club's) is polled once and fanned out, which also keeps Studio's load on PlayHQ flat as customers grow.
  • Rate limits and body size limits on every write route; a WebSocket fan-out that survives a few hundred pages per tenant (today's one-process design is fine for this size).
  • Observability: structured logs per tenant, an uptime check on the live feed, an alert when PlayHQ answers start failing (stream night is the only time that matters).
Matt does
Settles the PlayHQ question (M2) before this phase starts. Buys the domain and sets up DNS per tenant.
Done when
A Thunder League game is streamed with OBS loading every graphic from the cloud address, scoreboard latency under 2 s behind PlayHQ, and Matt's Mac closed.
Touches: server.js (start-up, routing), access.js, scene.js (socket, SSE), playhq.js (becomes a client of the shared poller), linkhost.js (tenant host), a new cloud/ folder or repo for the supervisor and worker. The pages change only where they build absolute links.
Phase 3

Operate from any browser

3 to 4 weeks

The Output page, Scoreboard control, Competitions setup, Sponsors and Athletes work as a signed-in web app. The Stream Deck plugin points at the cloud with a token. Studio is usable from a laptop, a tablet at the scorer's bench, or a phone.

Build
  • Sign-in and organisation switcher in studiobar.js; the Electron-only bits (Go menu, will-prevent-unload, the off-air page) behind feature checks that the pages already half have.
  • Music and sound in the browser: the Output page's preview sound exists; the on-air music player moves to whichever client is "the audio output" (the render agent in Phase 4, or the operator's browser until then).
  • The plugin's host setting becomes a tenant address plus token; the SSE feed gains the same token check.
  • Roles: operator can score and run scenes, owner can change setups and sponsors, viewer sees the Output page only. The sponsor report becomes a shareable read-only link for the sponsor.
Matt does
Decides which roles exist and what a club-level customer (not an association) can see.
Done when
A whole stream night is run from a browser and a Stream Deck with no Studio app installed.
Touches: public/studiobar.js, output.html, control.html, setup.html, music.js, plugins/studio-deck.
Phase 4

The Mac app becomes the render agent

3 to 4 weeks

The app stops running a helper. It signs in, picks an organisation and competition, connects to the cloud scene over the WebSocket, renders the scene locally in the existing off-screen window, and drives displays, NDI and DeckLink from that frame. Music plays here when the agent is present.

Build
  • desktop/scenewindow.js loads the cloud scene page instead of localhost:8080; desktop/outputs.js, ndi.js, decklink.js unchanged.
  • Offline grace: if the venue's internet drops, the agent keeps the last scene and the board keeps counting from the last PlayHQ reading; the Output page shows the health strip (D5) in red.
  • Updates stay on the existing release chain (electron-updater, signed, FirstPassStudio-releases).
Matt does
Keeps a local-only mode? See M10: the recommendation is to keep "run everything on this Mac" as a supported mode for one more year, because venue internet is the weakest link on stream night.
Done when
Thunder League goes out over NDI from the agent with the scene edited on another device.
Touches: desktop/main.js (no utilityProcess helper when signed in to the cloud), desktop/scenewindow.js, desktop/offair.html, outputs.js.
Phase 5

Billing, plans and running it as a business

2 to 3 weeks, then ongoing
Build
  • Stripe subscriptions per organisation; plans by number of competitions and outputs (M11). Usage caps on storage and viewer-count API calls.
  • A status page and an incident playbook for stream night; backups of Postgres and the bucket with a tested restore; a deletion flow for an organisation that leaves (and its athletes' personal information).
  • Terms of service, privacy policy (Australian Privacy Act; some players in 21&Under divisions are minors), a data processing note for associations.
  • Self-serve onboarding: template, PlayHQ link, first graphic, in under 15 minutes, measured.
Done when
Someone Matt has never met pays, sets up and streams without a support message.

Work that pays off whichever shape wins

These are code changes that make the move possible and make today's Studio better at the same time. They can start now, each as its own pull request, with no cloud account involved.

  1. A storage interface. Put every read and write of the data folder behind one module with a local implementation (Phase 1's first step). Today the modules call fs and savefile directly; test/packaging.test.js's file list is a ready-made map of what to cover.
  2. Tenant and actor on every request. server.js builds one req.studio = { tenant, actor } object and passes it to the modules' route functions. Today that is always { tenant: 'local', actor: 'this computer' }, which keeps behaviour identical while making the seam visible.
  3. Tokens on the Stream Deck links. An optional deckToken in config.json; when set, /deck/* and the SSE feed need it. Off by default today (Matt's rule: never remove manual controls), on in the cloud. This is S9's Stream Deck item.
  4. Pages that know their base. Every absolute link the pages build goes through one helper (linkhost.js on the server, one function in pageoptions.js on the client) so a tenant host is a one-line change.
  5. A PlayHQ client that can be shared. playhq.js already caches per query; give it an injectable transport so the Phase 2 worker can sit in front of it, and record every call's count and latency in the health strip.
  6. Run the helper without Electron in CI. It already does (the Tests workflow); add a Dockerfile and a container test so Phase 2 starts from a known-good image.

Suggested order

  1. Decide M1, M8 and M11 (shape, licence, price) so Phase 0 has a product to point at.
  2. Start the "pays off either way" list as pull requests now: storage interface, tenant seam, deck tokens, link base, PlayHQ transport, Dockerfile.
  3. Open the PlayHQ conversation (M2) early; it will take longer than any code.
  4. Phase 0 and sell one copy to a second association, which proves the first-run experience.
  5. Phases 1 and 2 once M2 is answered, with Thunder League as the first cloud tenant and Matt's Mac as the fallback.
  6. Phases 3, 4 and 5 as customers ask for them.

Rough total for shapes B through Phase 5: about 20 to 27 weeks of focused work, spread across a season. Phase 0 alone is 3 to 4 weeks. These are estimates, and the PlayHQ answer can move the whole plan.

What this plan does not do

  • It does not change any code. Each item becomes its own pull request once Matt approves it, as the two reviews did.
  • It does not pick vendors beyond a recommendation; Supabase and Fly.io are named because the FirstPass family already leans on Supabase and because the helper is plain Node.
  • It does not settle the PlayHQ question. That is a conversation with PlayHQ, and it is the thing to start first.
