FirstPass Studio · application security review · 24 October 2026

Safe enough for one Mac today. One fix matters now; the rest is groundwork for a product.

This review read the helper and its modules, the Mac app, the Stream Deck plugin, the four GitHub workflows, the release and update chain, the dependency trees and the tests, and ran npm audit on both package trees. It rates each finding twice: for how Studio is used today (one copy on Matt's Mac, on a home or venue network), and for what would matter if Studio is later licensed to other associations or run in the cloud as a service.

Nothing here comes from an incident. No code was changed for this review; each decision Matt approves becomes its own pull request.

The threat model, in one paragraph each

TodayStudio runs as Matt's user on his Mac and listens on every network interface on port 8080. Who can reach it: anything on the same Wi-Fi, and any web page open in a browser on the Mac. What is at stake: the stream (someone changes a score or a scene mid-game), and the data Studio holds (athlete names and photos, sponsor details, stream API keys).
Licensed appOther associations install the same signed Mac app and update from the public releases repository. What is added: the app runs on machines Matt doesn't control, so the update chain and the binary's own hardening carry the trust, and each customer's data is theirs.
Cloud serviceMany tenants share one deployment reachable from the internet. Everything that is "the network is trusted" today becomes authentication, tenancy, quotas and audit. That is a redesign of the trust model, not a list of patches, so it is treated as a separate section at the end.

What is already right

These were checked and need no change. They are worth knowing so the decisions below don't re-cover ground.

No CORS header (D3 of the architecture review)send() sets no access-control-allow-origin, so a page from another site cannot read anything from Studio in a browser. The test in test/access.test.js pins this. The gap it leaves (writing without reading) is finding S1.
"Let other devices change things"access.js refuses changes from other addresses with a 403 that explains itself, counts every address the Mac owns as local so the .local name keeps working, and is a tray tick box. Reads stay open on purpose.
File paths are disciplinedEvery upload name goes through path.basename plus a character allowlist and an extension allowlist; competition and sponsor ids match ^[a-z0-9-]{1,40}$; the settings restore checks every path part of every zip entry and refuses .., absolute and backslash paths; the static server normalises and prefix-checks against public/. No traversal was found.
Stream keys stay on the MacYouTube keys and Facebook Page tokens live in stream-keys.json, which is in LOCAL_ONLY: never moved to iCloud, never in a backup zip, and the API returns only hasKey, not the key.
The app's windows are sandboxedEvery Studio window is created with contextIsolation: true, sandbox: true, nodeIntegration: false, no preload, new windows only for Studio's own address, everything else handed to the browser. The output and scene windows use Electron 45's defaults, which are the same.
Updates are signed twice overThe app is hardened-runtime signed and notarised; latest-mac.yml carries a SHA-512 the updater checks; and Squirrel.Mac refuses an update whose code signature doesn't match the running app. A stolen releases token alone cannot ship code to installed apps.
CI tokens are least-privilegeTests run on pull_request (not pull_request_target) with contents: read and no secrets, so a pull request from a fork of the now-public repository gets nothing. Only merges to main reach the signing secrets.
No shell stringsEvery child process (ffmpeg, scutil, osascript, brctl, open) is started with execFile or spawn and an argument array; no user text reaches a shell. The JXA font scripts take the font name as argv, not by string building.
Dependencies are currentAll five direct dependencies are at their latest release (Electron 45.0.0, electron-updater 6.8.11, electron-builder 26.18.0, Playwright 1.64.1, qrcode-generator 2.0.4), Dependabot runs monthly on three ecosystems, and the helper itself runs on Node alone with two runtime packages.

Findings

S1

Refuse changes that come from another website's page

High todayHigh later

Finding. Dropping the CORS header (D3) stops other websites reading Studio, but browsers still send cross-site requests without asking. Any web page open in any browser on Matt's Mac, or on any device on the same network, can make the browser fire GET http://localhost:8080/deck/home/add2 with a hidden image tag, or POST /api/scoreboard, /api/scene, DELETE /api/scene/media or /api/setup-template with a body, because readBody parses the body as JSON whatever the content type and nothing checks where the request came from. The request arrives from the Mac's own address, so "Let other devices change things" being off does not help. A DNS rebinding page gets the same result against the .local name. The WebSocket at /api/scene/socket also accepts any origin, which lets another site read the scene and board (read only; it takes no commands).

The realistic shape today is a stream being tampered with by a malicious or compromised page Matt happens to have open on stream night. Unlikely, but the fix is a dozen lines and removes the only way a remote party can change Studio without being on the network.

Recommend
In the request handler, for every request access.changes() already classes as a change, and for the WebSocket upgrade: if the request carries an Origin header (browsers always add one to cross-site requests and to all POSTs), require its host to be one Studio answers to (localhost, 127.0.0.1, the link host, the Mac's own addresses) on Studio's port; otherwise answer 403 with a plain message. Requests with no Origin (the Stream Deck plugin, Stream Deck "Website" keys, curl) carry on unchanged. Also check the Host header against the same list, which closes DNS rebinding. Pin both with tests in test/access.test.js.
Alternative
Require a token on every changing request. Stronger, but it breaks every existing Stream Deck "Website" key and the plugin, so it belongs with S9, not now.
Risk
Low. Studio's own pages send Origin: http://<host>:8080, which passes. The one thing to test by hand is a page opened by the .local name on a phone.
Evidence: server.js send() comment ("a web page from anywhere else can't read or drive Studio", which is true for read, not drive); readBody(); access.changes(); scene.js upgrade() checks only the path and key.
S2

Keep the backup, the athlete register and the log to this Mac when other devices are locked out

Medium todayHigh later

Finding. Reads are open to the whole network by design, so the graphics work from other devices. But a few reads are not graphics: GET /api/settings/export downloads a zip of every setting, every logo, every athlete photo and all media; GET /api/scene/export does the same for the scene; GET /api/athletes returns the register of players by name; GET /api/log returns the whole debug log; GET /api/sponsors/report returns the sponsor exposure figures. On venue Wi-Fi, anyone who finds matts-macbook-pro.local:8080 can take all of it, and untick or not, the switch doesn't cover reads.

The athlete photos and names are personal information about other people's children in some divisions, which is the part worth taking seriously today.

Recommend
Add a small list of sensitive reads to access.js (settings and scene export, athletes, log, sponsor report and nights, viewer settings) that follow the same remoteChanges switch: when it is off, they answer only this Mac. Graphics, the scoreboard, the ladder, media files and the scene state stay open so the Output page, OBS and the Stream Deck keep working from anywhere. Describe it on the Docs page under the switch's existing paragraph.
Alternative
A second switch, "Let other devices read private data". More to explain for little gain; the one switch already means "I'm on a network I don't trust".
Risk
None on stream night: all of these are Studio-page or browser reads, not graphics.
Evidence: routes in server.js (/api/settings/export, /api/log, /api/athletes), exposure.route(), scene.route() /api/scene/export; access.changes() covers only non-GET and /deck/.
S3

Serve uploaded files so they can't run as Studio

Low todayMedium later

Finding. Logos, brand images, photos, sponsor logos and media files are served from Studio's own origin with the type taken from the extension and no Content-Security-Policy. SVG is on the allowlist everywhere. An SVG file can carry a script, and opened directly at /logos/x.svg that script runs with Studio's origin, from which every API is reachable. Today only Matt puts files there. But a competition template (templates/*.json, imported with "Import a template file") carries logos as base64, and templates are exactly the thing that would be shared between associations once Studio is licensed. cleanUrl() for browser sources strips a leading javascript: once and lets anything else through; there is no check that uploaded bytes match their extension.

Recommend
One header pair on every response that serves an uploaded or imported file (/logos, /brand, /photos, /fonts, /media, /sponsors): Content-Security-Policy: sandbox; default-src 'none' and X-Content-Type-Options: nosniff. Images still render inside <img> tags; a script inside one no longer runs as Studio. Parse browser-source URLs with new URL() and allow only http:, https: and relative paths. Check the first bytes of image uploads (PNG, JPEG, GIF, WebP signatures; SVG must parse as XML with an <svg> root).
Alternative
Drop SVG from the allowlist. Simpler, but club logos are often SVG.
Risk
Low. sandbox on an image response has no effect on how pages display it. The page test opens every page in Chromium and would catch a broken logo.
Evidence: competitions.IMAGE, sponsors.js IMAGE, scene.js MEDIA_TYPES and sendMedia(); server.js /logos|brand|photos|fonts/ route; scene.js cleanUrl(); no CSP header anywhere in server.js or public/.
S4

Finish hardening the Mac app: fuses, entitlements, asar

Low todayHigh later

Finding. The renderer side is done well (see "already right"). The binary side is on electron-builder's defaults. Three things follow. Electron's fuses are not set, so the signed app still honours ELECTRON_RUN_AS_NODE, NODE_OPTIONS and --inspect: any process running as the same user can launch FirstPass Studio.app as a plain Node and run its own code under Matt's Developer ID signature and notarisation. The default hardened-runtime entitlements include allow-dyld-environment-variables and disable-library-validation, which is what makes that and library injection (S7) possible. And asar: false leaves the app's JavaScript as plain files inside the bundle, so there is no integrity check on the code that runs.

Today this changes nothing: someone who can run code as Matt's user already has everything. It becomes the main question a security-aware customer or Apple reviewer asks of a licensed app, and signed-binary abuse is the standard way a hardened Mac is attacked.

Recommend
In package.json build: electronFuses with runAsNode: false, enableNodeOptionsEnvironmentVariable: false, enableNodeCliInspectArguments: false, enableCookieEncryption: true, and once asar is on, onlyLoadAppFromAsar: true and enableEmbeddedAsarIntegrityValidation: true. A build/entitlements.mac.plist with only allow-jit and allow-unsigned-executable-memory (Chromium needs those; the dyld and library-validation ones go, with S7 done first because the NDI library then has to be signed). Switch asar on with asarUnpack for vendor/ffmpeg/**, native/**/*.node and the Stream Deck plugin file; utilityProcess.fork of server.js works from inside an asar. Remove the Developer Tools menu item from packaged builds (keep it in npm run app).
Alternative
Fuses and entitlements only, asar later. Gets most of the value with less risk to the ffmpeg and native-module paths.
Risk
Medium: paths to ffmpeg, the .node modules and the plugin file change under asar. test/packaging.test.js and a test build from the Actions tab (Publish unticked) cover it before anything ships.
Evidence: package.json build has asar: false, hardenedRuntime: true, no electronFuses, no entitlements; build/ holds only icon.png; desktop/windows.js View menu has toggleDevTools.
S5

Narrow the release secrets and pin what the build runs

Low todayMedium later

Finding. Everything that lets Studio ship an update lives in five repository secrets: the Developer ID certificate and its password, the Apple ID, app-specific password and team id, and RELEASES_TOKEN, a personal access token that can write to FirstPassStudio-releases. Every merge to main runs with them. During that run npm ci executes the install scripts of about 290 packages (Electron and electron-builder pull most of them), npm ci runs again in two native module folders and the plugin folder, and the ffmpeg build clones three upstream repositories by tag with no commit pin. Each of those is code from outside the repository running next to the signing certificate. GitHub Actions are pinned to major tags (actions/checkout@v7) rather than commit SHAs, so a compromised tag would run too.

The signature check in the updater (see "already right") means the worst case for a stolen token alone is a broken or missing update; the worst case for a stolen certificate is a malicious update that installs. The latter is the one to make hard.

Recommend
One PR: pin the Actions to commit SHAs (Dependabot keeps them current, since the github-actions ecosystem is already configured); run npm ci --ignore-scripts then node node_modules/electron/install.js explicitly, so only Electron's own download runs as a script; pin the ffmpeg, libvpx and opus clones to commit SHAs beside the tags (the ffmpeg-updates workflow fills both in). One setting change outside the repo: make RELEASES_TOKEN a fine-grained token scoped to FirstPassStudio-releases only, Contents read and write, with an expiry, and put the five secrets in a GitHub environment named release that only the main branch can use.
Alternative
Leave the build as is and rely on the signature check. Reasonable while Matt is the only installer; not once others are.
Risk
Low. --ignore-scripts can break a package that compiles at install time; the Tests workflow uses the same install, so it shows up there first. The native modules keep their own npm ci plus build steps.
Evidence: .github/workflows/mac-app.yml (secrets, four npm ci, vendor/ffmpeg/build.sh fetch() with --branch "$2" only); .github/dependabot.yml. A stale comment in the workflow still says the repository is private; it has been public since 19 October.
S6

Turn on the free GitHub scanners and check runtime packages in CI

Low todayMedium later

Finding. npm audit today: in the main tree, one advisory, undici (denial of service), pulled in by @electron/get and node-gyp, which only run at build time. In the Stream Deck plugin, zod (memory exhaustion on oversized input) through @elgato/utils, which the plugin does ship but uses only to parse its own local settings, plus fast-uri and serialize-javascript in the Rollup build tools. None affects a running Studio. Dependabot version updates are configured; Dependabot security alerts and secret scanning are separate switches, free on a public repository, and nothing in the repo shows whether they are on. No workflow fails on a vulnerable runtime package, so a real one would wait for the monthly Dependabot run.

Recommend
Settings > Code security: turn on Dependabot alerts, Dependabot security updates and secret scanning with push protection (no PR needed, Matt does it). One PR adds npm audit --omit=dev --audit-level=high to the Tests workflow for the root and the plugin, so a runtime advisory turns a pull request red the same day. Bump @elgato/streamdeck when its next release carries the zod fix (the current 3.0.3 is the latest, so this is a wait).
Risk
None. A false positive makes a PR red once and is handled by a bump.
Evidence: npm audit --json at the root and in plugins/studio-deck, 24 October 2026; package-lock.json shows undici under @electron/get and node-gyp; the repository metadata returns visibility: public.
S7

Load only a signed NDI library

Low todayMedium later

Finding. NDI Tools doesn't install its runtime in /usr/local/lib, so desktop/ndi.js walks /Applications and /Library/Application Support five levels deep and loads the first libndi*.dylib it finds into the app. Any application bundle on the Mac that contains a file by that name gets loaded into FirstPass Studio with its signature and permissions. The disable-library-validation entitlement (S4) is what allows a library signed by someone else to load at all.

Recommend
Before loading a candidate, run codesign -dv --verbose=2 on it (via execFile) and accept only a library whose TeamIdentifier is Vizrt/NewTek's, or whose path is /usr/local/lib/libndi.dylib installed by the official runtime; log and skip the rest. This also lets S4 drop disable-library-validation once the accepted library is itself signed.
Alternative
Only load from /usr/local/lib and tell the user to install the NDI runtime. Simpler and stricter, but it removes the convenience the current search was written for.
Risk
Low. The NDI path is only used when an NDI output is on, and desktop/ndi.js already reports why the library wasn't found.
Evidence: desktop/ndi.js bundledCopies().
S8

Move keys and tokens into the Mac's Keychain

Fine todayMedium later

Finding. stream-keys.json holds YouTube API keys and Facebook Page access tokens in plain text, readable by any process running as Matt's user. The handling around it is careful (local only, never exported, never returned by the API), which is why this is fine for one Mac. A licensed app holding customers' Facebook tokens in a plain file is a different conversation, and so is the PlayHQ Client ID: apiKey is a competition setting, so unlike the stream keys it is in settings.json, in every backup zip, in an exported template and in the GET /api/setup answer. It is empty today.

Recommend
When licensing is real: keep the file but encrypt the values with Electron's safeStorage (Keychain-backed) when running in the app, falling back to plain text under npm start. Move apiKey from competition settings to the same store, and drop it from template export and the setup answer. Not before: the switch is a migration (migrations.js has the pattern) and gains nothing while there is one user.
Evidence: viewers.js KEYS_FILE, saveKeys(), hasKey; competitions.js DEFAULTS.apiKey; server.js CONFIG.apiKey as x-api-key.
S9

Authentication, tenancy and the PlayHQ question before any cloud move

Design first

Finding. Studio has no users, no sessions and no permissions. Its security model is "whoever can reach the port", narrowed by the one network switch. That is the right model for a tool that lives on the Mac next to the stream, and S1 and S2 make it a sound one. It cannot be stretched to a service. The following would each need a decision before a line of cloud code is written, and none of them is a patch to the current code:

  • Accounts and tenancy. Every path today is global: one data folder, one active competition, one board, one scene. A service needs a tenant id on every file and every route, and tests that one tenant cannot read another's.
  • Stream Deck links. The plain-GET /deck/ links are the point of the Stream Deck integration and cannot carry a login. Over the internet each one would need a per-tenant token in the URL or a header the plugin sends, with rotation.
  • Uploads. Limits are generous for one Mac (20 GB per video, 100 MB templates, 15 MB images) and there is no quota, no virus scan, and the files are served from the same origin (S3). A service needs per-tenant storage with quotas, a separate origin for user files, and S3 done.
  • Outputs are hardware. NDI, DeckLink and the full-screen output windows are local to a Mac. In the cloud the pages would be rendered by headless browsers and streamed, or the Mac app stays the renderer and only settings move to the cloud. That is the architecture fork to decide first.
  • PlayHQ terms. Studio reads PlayHQ's website GraphQL as a guest, not the licensed API. For one association that is what any browser does. A commercial service doing it for many customers, from cloud addresses PlayHQ may block, is a licensing and contract question to settle with PlayHQ before anything else, and the earlier note that cloud hosting was declined (11 October) still stands.
  • Error detail and the log. Error responses return err.message and 502s include internal detail; /api/log returns the whole log. Helpful on one Mac, wrong for a service.
Recommend
No work now. When licensing becomes concrete, a one-page design decision record on the fork above (Mac renders, cloud holds settings; or cloud renders) before any code, and then a second security review of that design. Everything in S1 to S8 is needed under either branch and is worth doing in the meantime.

Also checked, nothing to do

  • Request bodies. JSON bodies are capped at 100 KB; uploads stream to disk with per-kind limits and are removed on overrun.
  • Static server. path.normalize plus a prefix check against public/. The check compares against the folder name without a trailing separator, so a sibling folder named public-something would pass; none exists. Fold a path.sep into the check when S1 touches that code.
  • Settings restore. Zip entries are allowlisted by top-level folder, every path part is checked, each file is size-verified after unpacking, and the result is swapped in only when complete.
  • Page scripts. Of about 60 innerHTML uses in the pages, the ones that take PlayHQ or user text go through an esc() helper; the rest insert numbers, class names or single characters. One page option (?word= on streak.html) is inserted character by character without escaping; it is set per source by Matt on the Output page, so it needs a crafted link to matter.
  • Secrets in the repository. A scan of every tracked file for GitHub, Google, Slack, Meta and private-key patterns found nothing but a base64 PNG in a template.
  • Electron process isolation. The helper runs as a utilityProcess, not in the main process; a crash there restarts it without taking the app down.

Suggested order

  1. S1 same-site and host checks on changes (the one real fix for today).
  2. S2 sensitive reads follow the network switch.
  3. S6 scanners on, audit step in Tests (Matt flips the settings; one tiny PR).
  4. S3 headers on served uploads, URL parsing, image signatures.
  5. S5 pinned Actions and clones, --ignore-scripts, scoped token and release environment.
  6. S7 signed NDI library only.
  7. S4 fuses and entitlements, then asar, each verified with a test build.
  8. S8 and S9 wait for licensing to be real.

Each decision becomes its own pull request, built only once Matt approves it, with the Mac app workflow's test build used before anything that touches the binary is published.
