FirstPass Studio · 4K output plan · 27 October 2026

Taking Studio's outputs to 2160p

Matt asked what going to 4K would take: whether Studio should draw everything at 4K and scale it down for 1080p outputs, how much work it is, how hard, and what it does to the app as it is now. This is a plan only. Nothing here is built yet.

"4K" here means UHD, 3840 x 2160, the size broadcast gear and NDI call 2160p. Effort figures are days of focused work by one person with Claude and are estimates. Performance figures are worked out from frame sizes, not measured; the first PR exists to measure them on the M1 and the M3 Pro.

The short answer

No, don't draw at 4K and scale down. Each output already has its own off-screen scene window drawing its own graphics, so a single 4K picture would never be shared, and every 1080p output would pay four times the work to end up with the same picture it gets today. Instead, each output draws at its own format: a 1080p output stays exactly as it is, and a 2160p output draws the same 1920 x 1080 layout at twice the pixel density.

Effort: medium overall, in five small PRs (about 4 to 5 days) plus one large optional performance PR (1 to 2 weeks) that only happens if the measurements say so. Complexity: low in the pages, moderate in the render path, high only in that optional PR. Backwards compatibility: full. No setting, scene, sequence, Stream Deck key or page link changes meaning, and 1080p stays the default.

One thing to weigh first: the gear on stream night is HD. The ATEM Mini Extreme takes 1080p at most, and the UltraStudio that's there now is an HD-SDI model. 4K out of Studio only pays off with a 4K destination: a 4K switcher, a 4K NDI receiver, or a 4K display. PR 1 is cheap and useful for testing either way; the rest can wait until there's a 4K destination.

How Studio draws today

Every graphics page (43 in public/) is laid out on a fixed 1920 x 1080 frame. scene.html stacks the scene's sources as iframes on that frame, and fit.js, the scene's placements and the whole-pixel centring rule all work in those 1920 x 1080 units.

  • Display outputs (desktop/outputs.js) open scene.html?fit=1 full screen; it scales the 1920 x 1080 stage to the window. On a 4K TV that macOS runs as "looks like 1920 x 1080", the window is 1920 x 1080 points at 2x, so the scene is already drawn with 3840 x 2160 real pixels today.
  • NDI and Blackmagic share desktop/scenewindow.js: an off-screen, transparent Electron window at the format's size and frame rate. Each paint is copied out as a BGRA bitmap (image.toBitmap()) and handed to native/ndi or native/decklink, which convert it on the CPU (fill, key, chroma, straight alpha) and send the latest picture every frame.
  • 720p NDI already works by scaling: the window is 1280 x 720 and scene.html?fit=1 scales the 1920 stage by 0.667. 2160p is the same idea at 2x.
  • NDI formats are a fixed list in outputs.js (1080p and 720p, 25 to 60). Blackmagic modes come from the device but are filtered to 1080 progressive. The NDI module already accepts frames up to 7680 x 4320.
  • Off screen, the window is first made at 1 pixel per point. If macOS won't make it that big, it falls back to half size at twice the density. That fallback once looked soft at 1080p, which is the main thing PR 1 has to settle at 2160p.

The three options

A. Draw everything at 4K, scale down for 1080p

One 3840 x 2160 picture per output, shrunk for any output that runs at 1080p.

Four times the drawing, copying and converting for every 1080p output, plus a scale step on the CPU or GPU, for the same 1080p picture as today. Downscaling also smears the whole-pixel sharpness work from PR #119. Outputs don't share pictures (each has its own graphics), so there's nothing to save by drawing once. Not recommended

B. Each output draws at its own format

Pages stay laid out at 1920 x 1080. A 2160p output draws that layout at 2x density in its own window; 1080p and 720p outputs don't change.

Only the output that's set to 4K pays for 4K. Pages, fit.js, scene placements and links keep their units. Text, SVG and CSS come out sharp at 2x for free; only bitmaps (canvases, small logos, 1080p videos) need attention. Recommended

C. Re-lay every page out at 3840 x 2160

Change the design frame itself to 4K.

Every page, every scene placement, fit.js's zone, the Output page preview and every page link changes, and 1080p becomes the scaled-down case of option A. Weeks of work and a break with every saved scene, for nothing B doesn't give. Not recommended

The render path under option B

The page's layout is unchanged; only the window's pixel density changes with the format. Green is new or changed.

Two ways to get the 2x, and PR 1 tries both on the Mac and keeps the sharper one:

  • 2x density (preferred): the off-screen window is 1920 x 1080 with deviceScaleFactor: 2. Pages see a 1920 x 1080 window with devicePixelRatio 2, so canvases and images can ask for 2x pictures. This is the path that looked soft at 1080p once, so it has to be checked by eye and in the log ("scene drawn at ... at 2x").
  • 2x scale: a 3840 x 2160 window at 1x, with scene.html?fit=1 scaling the stage by 2, which is what 720p does at 0.667 today. Chromium redraws scaled text and vectors at full sharpness, but pages can't tell they're being drawn at 2x, so canvases stay soft, and macOS may refuse a window that big.

Pages and assets at 2x

  • Text, SVG, CSS shapes and gradients: sharp at 2x with no changes. Fonts are vector.
  • fit.js and placements: unchanged. They work in layout pixels, and a whole layout pixel is two whole device pixels, so the PR #119 sharpness rule still holds.
  • Canvases: three pages draw on air with canvases that have a fixed 1920 x 1080 backing (The Clash sparks and embers, the winner confetti, streaks). At 2x they'd be upscaled and soft. Each needs its backing sized by devicePixelRatio and its drawing scaled once, which is a small change per page.
  • Logos and photos: a picture is sharp at 4K if it has at least twice as many pixels as the layout size it's shown at. Team logos at 512 px are fine at most sizes; the 540 px winner crest needs about 1080 px; small sponsor logos will look soft. Studio can say so where pictures are added, as it already does for videos without transparency (PR #73).
  • Videos: 1080p videos are scaled up on a 4K output and look like 1080p video. The conversion to WebM keeps the original size, so a 4K ProRes becomes a 4K WebM, with the decoding cost above.
  • Stinger file: docs/stinger/render.js can render a 2160p ProRes 4444 by setting the browser's scale factor to 2. Expect files about four times as big (around 150 MB for the 0.5 s hold).

Backwards compatibility

Settings No new fields. A 2160p output just stores a new format name (ndiFormat: "2160p50", or a Blackmagic 2160p mode). An older Studio that reads it falls back to 1080p50, which outputs.js already does for any format it doesn't know.
Scenes and sequences Placements and scales stay in 1920 x 1080 units, so a scene looks the same on a 4K output, only sharper.
Page links Every page keeps its link and stays 1920 x 1080 when opened on its own. PR 4 adds an opt-in ?fit=1 to any page, so another app can open it at 3840 x 2160 and get it drawn at full size.
Stream Deck and /deck links Unchanged. They pick outputs, not formats.
Default 1080p50 stays the default for new outputs, and nothing moves to 4K by itself.
Manual controls None removed. The format picker gains entries; nothing else on the Output page moves.

The PRs

One change per PR, in this order. PR 1 to 5 together are a build-minor feature.

PR 1

NDI at 2160p, and the 4K render path

1 to 1.5 days
Change
outputs.js adds 2160p25 to 2160p60 to the NDI formats. scenewindow.js draws formats wider than 1920 at 2x density (or 2x scale, whichever PR 1 shows is sharper on the Mac). The Output page labels them "2160p (4K, about four times the Mac's work)".
Proves
Sharpness, and per-output CPU, memory and frame rate on the M1 and M3 Pro with one, two and four 4K outputs, from the perf meter's log lines.
Tests
Format list and settings round trip; an older settings file still loads as 1080p50; scene window size and density per format with the NDI stand-in.
PR 2

Blackmagic 2160p modes

0.5 day
Change
List 2160p progressive modes the device names, with the same "(device says it can't)" marking as PR #326. Default stays 1080p.
Risk
Can't be tested on hardware until there's a 4K Blackmagic device; only the stand-in library. Whether the device keys at 2160p comes from its own mode list.
PR 3

Sharp canvases and picture size warnings

1 day
Change
The three canvas pages size their backing by devicePixelRatio. Where logos, sponsor pictures and videos are added, say when a picture will look soft at 4K. Animations keep running by elapsed time.
Tests
Playwright screenshots of each canvas page at scale factor 2, checked for full-size backing.
PR 4

Any page at any size, and the docs

1 day
Change
A shared ?fit=1 for every page (scaling the 1920 x 1080 frame to the window, as scene.html does), listed in pageoptions.js. Docs page, "Data and bandwidth" (NDI at 4K), the user guide and its PDFs updated in the same PR.
PR 5

2160p stinger file

0.5 day
Change
docs/stinger/render.js takes a size option and renders 2160p ProRes 4444 at scale factor 2. Committed alongside the 1080p file only if Matt wants one.
PR 6, only if PR 1's numbers need it

Faster pictures off the GPU

1 to 2 weeks
Change
Electron 45's off-screen shared textures (useSharedTexture, an IOSurface on the Mac) instead of copying each bitmap through JavaScript, with fill, key and alpha worked out on the GPU or on the native module's own thread, and NDI given UYVA rather than BGRA.
Why it's big
New native code against IOSurface and Metal in both modules, a new failure mode (texture released too early), and it's the hardest part to test without the hardware.
